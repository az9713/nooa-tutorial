# System Design

This doc covers *why* NOOA is shaped the way it is — the decisions behind the architecture sketched in [`overview/what-is-this.md`](../overview/what-is-this.md), not a restatement of it. Read that doc first if you haven't; this one assumes the four core ideas (generation methods, docstrings-as-prompts, return-type-as-contract, pluggable strategies) as background.

## The organizing decision: agent-as-object, not agent-as-pipeline

The dominant pattern in agent frameworks circa the mid-2020s treats an agent as a pipeline: a prompt template, a tool registry, an orchestration graph, wired together by a framework-specific DSL or config format sitting on top of Python. NOOA's designers made the opposite bet — treat an agent as a Python object and let the language's own facilities (classes, methods, type annotations, docstrings) carry the weight that a separate DSL would otherwise carry. The [paper](https://arxiv.org/abs/2607.20709) frames this as bringing agent development back into reach of ordinary software engineering practice: testing, refactoring, static analysis, and version control all apply to an agent the same way they apply to any other Python code, because an agent *is* Python code, not a config artifact interpreted by a runtime.

This decision cascades into most of the framework's less obvious design choices:

- **A custom metaclass (`AgentMeta`) instead of a decorator-per-method requirement.** Detecting `...` bodies at class-definition time means a plain method with a real body needs *zero* framework annotation to work as ordinary Python — the framework only intervenes where it has to (ellipsis-bodied methods). A decorator-based design (`@generate` on every LLM method) would have made the "regular Python vs. LLM-driven" distinction explicit in the source, at the cost of ceremony on every generation method; NOOA chose implicit detection via the ellipsis literal instead, betting that `...` is a distinctive-enough marker to read cleanly without an accompanying decorator.

- **The docstring is the prompt, with no template engine.** A separate prompt-management layer (files, template strings, a registry mapping method names to prompt IDs) is exactly the kind of "second thing to keep in sync with the code" the whole design is trying to eliminate. Making the docstring *be* the prompt means there is structurally nothing to keep in sync — the prompt is versioned, diffed, and reviewed exactly like the rest of the method.

- **Return-type-as-contract instead of manual output parsing.** Every generation method's return annotation is fed to the strategy as a validation target; callers never see "the model produced a string that might contain JSON." This mirrors ordinary Python's own contract mechanism (type hints + a validator, here Pydantic) rather than inventing an agent-specific validation layer.

## Event sourcing and serialized execution

The project's own one-line self-description, from `pyproject.toml`, is "code-generating agent orchestration system with event sourcing and serialized execution." Two decisions worth unpacking:

**Event sourcing** — every state change during a run (an LLM call, a code execution, a turn boundary, an error) is recorded as an immutable, ordered event, and conversation history *is* that event log rather than a separately-maintained transcript. The payoff: replayability (a trace is literally the event log, not a reconstruction), queryability (`EventQuery`, `self.events.query(...)`), and clean separation between the append-only history and the point-in-time snapshot mechanism used for save/restore (see [`concepts/execution-and-storage.md`](../concepts/execution-and-storage.md)). The cost is bookkeeping — everything that touches agent state has to go through the event manager rather than mutating state directly — which the framework hides behind `self.context`/`self.events` so application code rarely touches the event log directly.

**Serialized execution** — generation calls on a given agent instance are executed under a lock (`ActorRuntime`), so two concurrent calls to the same agent can't interleave LLM turns and corrupt shared event history. Nested generation calls (a CodeAct loop calling another generation method on `self`) inherit the parent's lock instead of deadlocking, which is what lets orchestration code freely call generation methods from inside other generation methods without the developer manually reasoning about lock ordering. The tradeoff is throughput: an agent instance processes one generation turn at a time, by design — parallelism across *different* agent instances is unaffected, and within a single agent, correctness of shared history was judged more important than intra-agent concurrency.

## Visibility: convention over configuration

"Visible by default, hide explicitly" (see [`concepts/visibility-and-context.md`](../concepts/visibility-and-context.md)) mirrors Python's own privacy convention (`_private` names) rather than introducing a parallel permissions system. The alternative — an explicit allow-list every method/field must be added to before the LLM can see it — would be safer by default but would also mean every new public method needs a second registration step, which is exactly the "keep two things in sync" failure mode the whole framework tries to avoid. The design instead accepts that visibility mistakes are possible (a method you forgot to mark `@hidden` becomes LLM-visible) in exchange for the common case requiring zero extra ceremony, and mitigates the risk by making hiding a single decorator/annotation rather than a separate config file.

## Strategies: an execution-detail abstraction, not a public API surface

Making the strategy a decorator attached to *how a method is solved* rather than part of *what the method's interface is* was a deliberate attempt to keep an orthogonality property: swapping `PredictStrategy` for `CodeActStrategy` should never require a caller to change. This is what lets `@strategy(...)` be added or removed as a pure optimization (cost, latency, capability) without touching call sites — the same reasoning that motivates keeping strategy objects themselves stateless-per-call and configuration-driven (`CodeActConfig`, `PredictConfig`) rather than accumulating mutable state across calls.

## The safety model: guardrails are cheap, containment is not free

The in-process AST validator and module deny-list (`src/nooa/runtime/code_validator.py`, `src/nooa/runtime/restrictions.py`) exist because most mistakes generated code makes are *not* adversarial — accidental blocking calls, obviously-wrong imports, syntax the model produced but didn't mean. Catching those cheaply, in-process, with no extra infrastructure, is worth doing even though it can't be a full security boundary. The framework is explicit, in both the README and the restrictions module's own docstring, that a static Python deny-list cannot contain genuinely adversarial code (`open()`, `importlib`, and reflection are all inherent escape hatches in the language itself) — so the design doesn't try to close that gap with more deny-list entries (an acknowledged unwinnable arms race) and instead pushes the actual containment requirement to OS-level isolation, offering an *optional*, config-driven sandboxed execution backend (`execution_backend="sandbox"`, kernel-enforced via Landlock/seccomp/rlimits) as a middle ground between "no isolation" and "run the whole process in a container/VM." See [`concepts/execution-and-storage.md`](../concepts/execution-and-storage.md) for the mechanism, and note that even the sandboxed backend is presented as complementary to, not a replacement for, OS-level isolation of the whole agent process.

## Workspace package boundaries

The repository is organized as a `uv` workspace with the core `nooa` package plus four separately-versioned members: `nooa-cli` (CLI + trace viewer + eval runner), `nooa-memory` (long-term recall), `nooa-bench` (benchmark harness), and `eval_pipeline` (not published to PyPI). The boundary was drawn along "does a typical agent-writing consumer need this at import time" — the core framework has exactly three runtime dependencies (`pydantic`, `litellm`, `httpx`, plus `openinference-instrumentation-litellm`), while the viewer's web stack (FastAPI, uvicorn), the CLI's dependencies, and the memory subsystem's vector-search dependencies are all opt-in extras or separate packages. This keeps `pip install nooa` fast and dependency-light for the common "just write an agent" case, at the cost of requiring an explicit extra/package install (`nooa[cli]`, `nooa-memory`, etc.) for anything beyond that — a deliberate trade documented in the root `README.md`'s "Optional sub-packages" section.

## Research-software framing

The project ships with an explicit, prominent warning that it is research software, not a hardened production platform — LLM-generated code executed by a CodeAct agent can take unwanted actions, and the framework's own containment story (above) depends on the operator adding isolation the framework itself doesn't force. This framing shapes several choices visible elsewhere in this documentation: the `Development Status :: 3 - Alpha` classifier in `pyproject.toml`, the `CHANGELOG.md`'s current single entry ("Initial public release"), and the safety note repeated verbatim in both `README.md` and the restrictions module. Treat version-specific claims in this documentation (exact CLI flags, exact config defaults) as tied to the commit they were written against, and re-verify against `CHANGELOG.md` / `nooa --version` for anything load-bearing.
